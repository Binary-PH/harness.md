# Changelog

## 1.10.0 (2026-10-24)

- `docs/planning.md`: a new page, planning before code. How much planning a change needs (a fix with an obvious scope is its restatement and one slice; a bug whose cause is unknown is debugged first); the order of decisions, moved here from `docs/playbooks.md` and extended: assumptions listed and open points asked one question at a time with the assumed answer; research into how large engineering organisations and reputable open-source projects solve the same problem (their design proposals, decision archives, postmortems, standards and source), with what makes a project reputable, what to do when none qualifies, and the sources named in the project's plan; the official documentation of the exact version in use, with a pattern it does not cover called unverified and the existing code followed until the owner settles a disagreement. The plan's headings (goal, non-goals, success criteria a test or a measurement can check, approach, options considered, risks and the way back, open questions); thin vertical slices, the riskiest first, each with acceptance criteria and its test; a plan that spans sessions or pull requests kept in `docs/context/plans/`, on the working branch until it merges with the first pull request; one owner's go for a plan and its later releases; decision records that are superseded, never edited.
- `HARNESS.md` section 3, now "Plan, then build in slices": the whole order for a feature or anything larger, step 1 and one slice for a small fix; the research and documentation orders; the plan; and the term "hard to undo", defined once (a revert of the merge does not bring back what was there: a migration that drops or rewrites data, an interface or file format others already read, anything that moves money, a deletion of user data, anything else a revert would not restore). A plan for a new project or a change that is hard to undo waits for the owner's go; any other plan goes into the pull request text. While coding: one slice at a time, proved by the runner; a test seen failing first where behaviour changes, with the project's test tool on that one test and the run's test database, while every green proof is the runner's, so no passing test runs twice; a refactor needs no new test; debugging in order, with a FAILED step stopping new work and a BLOCKED one stopping only its merge; the simplest form that works.
- `HARNESS.md` section 2: a problem noticed outside the task is listed, not fixed, unless it blocks the merge, when it is fixed in a change of its own that merges first; a clear problem with the approach asked for is said once with its cost. A part merged behind a feature flag that is off bumps the third number, and turning the flag on bumps the second.
- `HARNESS.md` section 2, `docs/testing.md`, `docs/playbooks/interactive-web.md`: "Both themes readable" becomes "Text readable on its background", for every user interface and not only one with two themes, with numbers: a contrast of at least 4.5 to 1, and 3 to 1 for large text, icons, field borders and focus outlines; text over an image, a video or a gradient gets a backing. A web front end measures it once, with an automated contrast check on the desktop profile in the run that already covers every appearance, and judges text over images on the screenshot of that run; a native app uses its platform's accessibility checks. Before, "readable" had no measure and a single-theme interface had no rule.
- `docs/code-review.md`: a new page, the review of the diff: tests first; five points (correct, plain, in place, light, clean); no check made easier to pass (a skipped, deleted or weakened test, a removed assertion, a suppression without its review comment, a blanket disable, a lowered threshold, a stub or an empty error handler), each put back or named for the owner's go, while a test removed with its behaviour, a reviewed false positive and a flaky-list entry follow their own rules; a size a reader can hold, without lock files or generated files; for a change that is hard to undo, a second reader who did not write it, three rounds at most.
- Ship step 3 (`HARNESS.md` section 7, `docs/shipping.md`): the reviews come before the merge's runs, the security review (scoped, or full with the expensive tier) and then the review of the diff, which so reads the security fixes too, so a fix they bring is checked by those runs once; a confirmed security finding in the change blocks its merge and is fixed in that pull request; step 3 names tier 2 with its `expensive` suites; step 9 names the build scripts' release run. The pull request text, in the entry file, the step and the template alike, gains the plan, the FLAKY steps and the flaky list, feature flags, the review and the way back.
- `docs/testing.md`: how to write a test (most tests small, real code before stand-ins, outcomes instead of calls, one behaviour per test, seen failing once) and how to debug a FAILED step (stop the line, read the kept log, reproduce with the one test, localize, reduce, fix the cause, then the runner once, with no extra full run). Tier 1 is each slice and each update of a pull request. Lanes say an earlier step stopped the lane, not that it failed; the run folders of BLOCKED and FLAKY steps are kept, and so is a log a flaky entry points at; a step joins the flaky list through a pass of the same code in another run. The in-app browser profiles run only what differs from their phone: layout, safe areas and fallbacks.
- `docs/shipping.md`: changes a running version must survive: a schema change expands and then contracts over releases; an interface others read gains and loses fields only through a deprecation; a part users must not see yet merges behind a feature flag that is off, whose configuration file is in the paths of the suites it gates; and the way back: a broken live release is reverted through the ten steps before it is debugged, a change that is hard to undo takes the way back its plan wrote, data comes back only through its migration's own way back, and the owner decides when neither restores the flow. A revert whose tree equals a release tag needs no new security review. One run proves one tree when the host runs checks too.
- Less redundant checking, and the gaps it left closed. The gate skips a step, or a file, that came out with no blocking row on identical files, configuration, tool version, rule packs and check command, and prints `skipped (clean on identical files)`; the dependency step's record lasts one day, so the scans at a commit, before the merge and at packaging do not repeat each other. Each suite's hash covers its own entry in the filters file, not the whole file, so a change to the filters file runs only the suites whose entry or files changed, and never an uncached suite for an edit elsewhere; the hash covers untracked files and the manifests too, and the pass cache keeps the passing hashes of the last three release tags, so a revert reruns nothing that passed. End-to-end baselines are kept per schema hash, so a revert or a switch of branch never loads a baseline built for another schema. An `uncached` suite runs only in the expensive tier and when the owner asks, so neither tier 2 nor `--release` calls an outside service. A new entry on the known-flaky list waits for the owner's go, and a revert bumps the third number. The build scripts run their unit suites through the runner and no second type check. The interactive web playbook leaves phone width and reduced motion to the browser profiles and runs its smoke test in the desktop profile's suite; the search playbook checks page heads once, in a suite after the build instead of a gate step, the live sitemap once, and compares its baseline only after a release that changed public pages. The security review caps its gap passes at three and carries an unchanged confirmed finding over. Gaps closed: a change to a lock file, a manifest or the setup script, other than the version bump, now reaches the type check, the typed lint rules and every suite of its part, so a new dependency is always tested; the secrets scan covers every tracked file, and the build scripts scan their built output for secrets and source maps; Markdown, shell and container files reach their linters in changed mode.
- Wording: one gate mode per moment (changed before a commit, full in the build scripts); a blocking gate row inside a test run gets its verdict from its log; the `--changed` base is named; exit code `0` lists skipped steps; "run plan", "options" and "test tool" each have one meaning; a retired lesson is renamed, never edited; "checks of the deployed surface" throughout; `docs/playbooks.md` holds only what a kind of project adds; `docs/testing.md` loses a repeated rate-limit line; `HARNESS.md` section 5 has one introduction to the tiers.
- `README.md`: a centered title, tagline and row of links; the three stretches of a task; a diagram of the loop in a light and a dark version, with alt text that carries all of it; a "How it works" section; the parts and files for the new pages, with the file list folded; a contributing section. `CONTRIBUTING.md`: README images are PNG files in `assets/` with a dark variant and full alt text, never SVG or a badge from another host; the decisions add text readable on its background, the planning research, and the no-rerun rule for gate steps and the filters file.

## 1.9.0 (2026-10-23)

- `HARNESS.md` section 5, `docs/testing.md`: a new verdict, FLAKY. A step on the known-flaky list (now `flaky` in the filters file, each entry with the date and the log that put it there) that fails runs again at once, once, without a fix; a pass makes it FLAKY, a second failure FAILED. FLAKY does not fail the run and is never a clean pass; the list is a queue to fix and every pull request text names its entries. Before, a flaky step was reported FAILED, which elsewhere means the code is wrong, and the rerun's effect was unclear.
- `HARNESS.md` section 5, `docs/testing.md`: the exit codes split code from environment: `0` passed, `1` FAILED, `2` preflight (the BLOCKED verdict caught before anything ran), `3` nothing failed but a step was BLOCKED or did not run. A suite the filters leave out or the cache skips is `skipped`, never not run. A release run is defined.
- `HARNESS.md` sections 4 and 7, `docs/code-check.md`, `docs/shipping.md`: a full gate run runs every step and `--changed` the steps the files reach (the old "every step always run" said otherwise); the text rules skip vendored folders in the entry file as on the detail page; the expensive tier takes the place of tier 2 for its merge; the version is counted from main at merge time, so two branches never claim one number; ship step 4 names the memory snapshot; step 7 says what a project without a health endpoint checks.
- `HARNESS.md` sections 1, 2, 8, 9, `docs/lessons.md`: where a copy's `docs/` lives; the address's main branch holds the latest release; the update check takes only plain release tags, treats an empty list as not checked, and leaves the replacement to a session that changes files; the checks an order runs on its own are not scope creep; the expensive tier is an allowed whole-project sweep; the inbox and the snapshot have their paths in the entry file.
- `HARNESS.md` section 5, `docs/testing.md`: no test runs twice for the same result. The pass cache now holds in every tier, the expensive tier and a release run included, and its hash also covers the setup script and the lock files, so a new tool, browser or dependency still forces a run. A suite that depends on something outside the repository is marked `uncached` and runs whenever selected; `--no-cache` stays for the owner's ask. Before, the expensive tier and a release run re-ran suites that had already passed on identical code.
- `HARNESS.md` section 5, `docs/testing.md`, `CONTRIBUTING.md`: the device profiles beyond desktop and Android (iPhone, the in-app browsers, the other desktop engines) run once before a merge whose change reaches the front end, as well as in the expensive tier, so a front-end change never ships untested on a profile and no profile runs on every commit. A suite marked `expensive` now runs with `--since` when its paths match. Before, a run of small releases left those profiles unrun.
- `HARNESS.md` sections 4 to 7 and the detail pages, from a question-led cold read: a flaky failure with an environment cause is BLOCKED; FLAKY keeps its lane, its log and its merge, and counts as a pass for the cache; the flaky list sits outside the cache hash and the version number too, so adding an entry or renumbering reruns nothing; resuming is for after a fix; `--dry-run` exits 0; the A/B rule takes the old result from the history; a schema change runs the end-to-end suite so the baseline matches; the dependency scan covers every lock file before a merge (a new `--deps` switch of the check command, run in ship step 3) and the update bot covers an idle project; a missing tool inside a test run is caught by the preflight and a gate finding is FAILED; the full security review replaces the scoped one; lessons are saved before the snapshot is refreshed; BLOCKED steps are run again with the runner, not by rerunning a host workflow; the update check says which copy each session follows.
- `README.md`, `CONTRIBUTING.md`: the test runner line, the cold read questions and the decisions already taken say the same.

## 1.8.0 (2026-10-23)

- `HARNESS.md` section 1: a new order, a project's copy of the harness stays at the latest release. In the first report of each session the agent reads the release tags with git, compares the newest with the version in the title, and when it is newer replaces `HARNESS.md` and its pages in `docs/` from a depth-1 clone of that tag (removing the pages the release dropped, never a file the harness did not bring), reads the new file, and reports the old and new version with the CHANGELOG entries between them. The replacement ships as its own pull request and bumps the project's third number, as a dependency update does, and a release that changes the gate or the runner brings the project's check command and runner in line in a change of their own. No go is needed, because everyone follows the latest release. Without git or a network it reports `update not checked`. Reading the file from its address needs no check.
