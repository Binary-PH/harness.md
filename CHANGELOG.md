# Changelog

## 2.0.1 (2026-10-24)

- `CONTRIBUTING.md`: a standing rule from the owner, "Adding to the harness". Every request to add something is worked through six steps, the first five before any text is written: name the mistake it prevents or the gap it fills, fit it to the harness's logic (its moment, section and page, extending before adding), keep only the parts that change what an agent does, settle open questions by researching how large engineering organisations and reputable open-source projects handle them, keep it lean (nothing the tools already provide, nothing run twice on identical input), and leave no conflict.
- `CONTRIBUTING.md`, release step 4: a change to the gate or the runner also gets an implementation read on two different projects; the rounds of reads are set before they start; and a change that leaves the text of `HARNESS.md` as it was, apart from its version, needs no new cold read of it. The orders of `HARNESS.md` are unchanged; only its version moves.

## 2.0.0 (2026-10-24)

A rewrite of the orders for simplicity, at the owner's request on 2026-10-24 ("simple yet effective, not overengineered"), after the practice of reputable agent harnesses: the always-read instruction file kept short and limited to what an agent would otherwise get wrong, details read each time their situation comes, and mechanisms the project's tools already provide used rather than rebuilt. A long list of orders is followed less well than a short one, and a hand-built cache gives a wrong answer whenever an input is missed, which is where the 1.10 to 1.12 rounds kept finding problems.

- `HARNESS.md` is about 40 percent shorter. The same ten sections remain; a section with a page names it and the moment to read it, each time that moment comes. Rules for something a project may not have (a database, a web front end, an app, a deploy host) apply only when it has one.
- **Removed**, all added in 1.10 to 1.12: the gate's clean-record cache with its per-file records, cache tests and 24-hour dependency record; the filters file's `deps`, `tools`, `env` and `baseline` keys; the baseline step and its naming and retention; per-test-file closure records; the importer rule for type-aware lint; the check command's `--deps` and `--no-cache`.
- **In their place**: a plain pass record per suite decides whether it runs (its files, its own filters entry, the runner, the setup script, and the manifests and lock files of its folders with their version fields left out); inside a suite that runs, the test tool's own result cache or affected-test mode may narrow the tests. A run on a drifted tool neither uses nor writes records; a FLAKY pass counts; `--release` means suites only, the build script owns packaging; a project with one suite needs no filters file; a target may name a suite. The gate checks each commit's files before the commit (`--uncommitted`, renamed from `--changed`); before the merge `--merge` runs only what can have a new answer, the dependency scan and the whole-project type check and type-aware lint; the release build's full gate is the one run over every file. The tools' own caches speed it up; the command keeps none. A tool that could not run exits `3`, apart from findings. The static analyser's secrets pack is left to the secrets step, its web packs run where the project has what they cover, and the git history is scanned for secrets once, when the gate is first built. A project with a database builds each test database from its migrations and seed data, and may keep a dump of a slow seed named by the hash of the files that build it.
- **Any project**: a published package is checked on the registry once the gated build publishes it, an app in a store is live when the store releases it and its way back is a new build, and an existing project with many findings may have them accepted by the owner as a recorded list that blocks nothing until worked down, while new findings block.
- **Added**, from long-running agent harnesses: a session starts by reading `git status`, the recent log and the open plan file, and ends with the work committed, the plan file updated and every server stopped; a slice is marked done only when the runner shows its test passing, and "done" in a report comes with the command that proved it.
- **Kept in substance**, as decided by the owner: no test or gate step run twice for the same result, FLAKY and the exit codes, the expensive tier on events, a copy at the latest release, the browser profiles, keys hidden on screen, text readable with its contrast numbers, the planning research, the playbooks' scope, and the security review's rules. The rules recorded in this session under the owner's delegation are kept where they are simple (one task, one branch, one pull request; a step blocked from outside merges only by the owner's choice; a new flaky entry waits for the owner's go) and dropped where they were machinery.
- `docs/testing.md` and `docs/code-check.md` are rewritten to match; `docs/shipping.md` step 3, `README.md` and `CONTRIBUTING.md` follow. `CONTRIBUTING.md` adds the decision "simple over complete".

## 1.4.0 (2026-10-21)

- `HARNESS.md` section 2: a new working rule, keys and passwords are hidden on screen. Where the product's user interface shows a saved key, token or other secret, takes one in, or takes a password, the field hides the value by default and a toggle beside it shows it and hides it again; the toggle works by keyboard and has a name a screen reader reads; every open of the view starts hidden and the shown state is never saved; a copy control may copy without showing.
- `docs/security.md`: the defensive design section carries the detail: where the rule applies (settings pages, forms, detail views, lists with one toggle per row, a field for a new key, every password field), the toggle's names, the shown state never saved, no secret in the page title, the URL or a log, a password field marked as a password.
- `CONTRIBUTING.md`: the decision is listed among the decisions already taken.
